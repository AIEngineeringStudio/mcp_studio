CHAPTER 01

Separate decisions from execution

Completed⌄
  • A host is the application coordinating the user experience.
  • A model generates text and may propose tool calls.
  • An MCP client is the protocol-speaking component used by the host.
  • An MCP server exposes operations or context.
+---------------------- Host ----------------------+
| User interface --> orchestration <--> model      |
|                         |                        |
|                     MCP client                   |
+-------------------------|------------------------+
                          |
                      transport
                          |
                     MCP server
                          |
                   ticket service
                          |
                     ticket store

A client is a role, not necessarily a separate operating-system process. A server can run in another process or machine; an in-memory test can place client and server objects in the same process.

CHAPTER 02

Trace the responsibilities

Completed⌄

Suppose the user asks “Is T-100 open?” The host chooses which capabilities to show the model and how to apply its approval policy. The model proposes get_ticket with ticket_id="T-100". The client encodes and sends that invocation. The server validates the request and dispatches to the handler. The business service reads the record. The client receives the result, and the host decides how to present or use it.

Discovery does not automatically place a tool into a model prompt. The host must translate or expose the discovered contract in the form its model API expects. This is why a successful scripted client proves protocol connectivity without proving a particular AI host will use the tool correctly.

CHAPTER 03

Ownership determines failures

Completed⌄

If a model chooses the wrong ticket ID, inspect host context and tool descriptions. If the subprocess cannot start, inspect client launch settings. If the tool is unknown, inspect registration and the discovered catalog. If the wrong user's ticket is returned, inspect server authorization and data access.

These are different layers. Changing the system prompt cannot repair a missing server executable. Changing transport cannot repair an authorization rule that trusts a caller-supplied tenant ID.

CHAPTER 04

Several servers

Completed⌄

A host may manage several client/server relationships. A ticket server and a document server can be separate integrations with different identities and permissions. A single server can also expose many tools. Neither “one tool equals one server” nor “one host equals one server” is a protocol rule.

Treat each boundary as a place where data and authority cross. A result from a document service is information, not an instruction to disable ticket-service access checks.

Worked observation:

In the supplied lab, client.py is a scripted caller. It has no model and no chat interface. This deliberately isolates discovery and execution from model selection and reasoning.

Professional articulation:

“The host owns orchestration, the client owns protocol communication, and the server exposes a controlled boundary around application capabilities.”
